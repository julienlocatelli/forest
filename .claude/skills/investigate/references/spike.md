# Technical question (spike)

A spike answers a technical unknown so a decision can be made: how something works, whether an approach is feasible, which option fits. It is time-boxed: stop at the answer, not at a full design.

The report covers:

1. **The question, made answerable.** Restate it so its answer is a fact or a choice. Split a broad question into the 2–4 sub-questions that decide it.
2. **Forest today.** How the repository handles the subject now, with `path:line` evidence, or that it does not handle it yet.
3. **Options.** At least two real options when the question is a choice, each with what it costs Forest (new dependency, files touched, risk) and what it brings.
4. **Feasibility.** For a "can we" question, the evidence that it works or the blocker that prevents it: a command run, a documented limit, an existing example.
5. **Recommendation.** One option, tied to the findings that support it.

Done when every sub-question has an evidenced answer or sits in the open questions.
